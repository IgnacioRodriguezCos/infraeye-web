PUNTO 3 — LIMITACIONES DE ISOLATION FOREST
================================================================================

EVIDENCIA ENCONTRADA EN EL CÓDIGO
---------------------------------
1. Sensibilidad al parámetro de contaminación (evidencia empírica en el
   propio proyecto):
   - src/models/anomaly_detector.py:17  -> default contamination = 0.1
   - src/main.py:27 y train_model.bat    -> el modelo final se entrena con 0.05
   - src/evaluation/find_optimal_contamination.py -> barrido de valores
     0.03 / 0.05 / 0.08 / 0.10 / 0.12 / 0.15 / 0.18 / 0.20 evaluados sobre
     datasets sintéticos con tasas de anomalía del 5%, 10%, 15% y 20%.
   - data/synthetic/optimal_contamination_results.json -> resultados: el mejor
     F1 medio se obtuvo con 0.03 (F1 = 0.418, precisión alta, recall bajo);
     con valores mayores el F1 decae. Es decir: el proyecto YA hizo la
     calibración empírica que justifica documentar la limitación.

2. Esquema híbrido: EXISTE en el código pero NO se usa en el flujo final.
   - src/models/anomaly_detector.py, líneas 97-163 (detect_anomalies_hybrid):
     combina Isolation Forest con reglas de negocio basadas en umbrales
     (cpu_max > 85/95, disk_max > 85/95, cpu_mean < 20 y mem_mean < 50 ->
     subutilizado, etc.).
   - VERIFICADO: ningún flujo de producción lo invoca. Todos los call sites
     (src/cloud/huawei_pipeline.py:304, src/main.py:89, web/app.py:326, 628,
     747 y 854, y los scripts de análisis) usan detect_anomalies(), es decir,
     Isolation Forest puro.
   - En el flujo final las reglas operan AGUAS ABAJO de la detección: el
     motor de recomendaciones (src/recommendations/recommendation_engine.py,
     invocado en huawei_pipeline.py:392) clasifica mediante umbrales (85/95,
     etc.) el TIPO de anomalía y genera acciones, pero únicamente para
     instancias que IF ya marcó como anómalas. La decisión is_anomaly es
     100% Isolation Forest.
   - Conclusión: la afirmación de la tesis "Isolation Forest como algoritmo
     único" (chapter02_antecedentes.tex:271) es CORRECTA para la versión
     final. El método híbrido es código experimental no integrado.

3. Alta dimensionalidad y mitigación:
   - src/data/preprocessor.py, líneas 100-129: se mitiga reduciendo el espacio
     a 15 características seleccionadas (media, p05, p95 por métrica) en lugar
     de usar todas las estadísticas calculadas (que serían ~50).

(A) chapters/chapter02_antecedentes.tex — insertar una subsección de
    limitaciones DESPUÉS del párrafo de ventajas (línea 115, "Entre las
    principales ventajas de Isolation Forest...") y ANTES del párrafo
    "En el contexto de INFRAEYE..." (línea 117):

    \subsubsection{Limitaciones de Isolation Forest}

    Si bien las ventajas descriptas favorecen la aplicación de Isolation
    Forest en escenarios de monitoreo de infraestructura, el algoritmo
    presenta limitaciones que condicionan su utilización. En primer lugar,
    los resultados dependen de manera significativa del parámetro de
    contaminación, que define la proporción esperada de observaciones
    anómalas y a partir del cual se establece el umbral de clasificación.
    Dado que dicha proporción no se conoce con anticipación en un entorno
    real, un valor subestimado reduce la sensibilidad de la detección,
    mientras que un valor sobreestimado incrementa la cantidad de falsos
    positivos \parencite{Liu2008}. En segundo lugar, el mecanismo de
    aislamiento resulta eficaz para identificar observaciones que se
    apartan marcadamente del patrón global, pero presenta dificultades
    para detectar degradaciones graduales del comportamiento, en las que
    cada observación individual resulta próxima a las consideradas normales
    y la desviación solo se evidencia a lo largo del tiempo
    \parencite{Natterdal2024}. Finalmente, aunque el algoritmo opera con
    eficiencia computacional sobre espacios de alta dimensionalidad, la
    presencia de características irrelevantes o redundantes degrada la
    calidad del aislamiento, por lo que su aplicación se beneficia de una
    etapa previa de selección de características \parencite{Zou2022}.

    En el caso de InfraEye, estas limitaciones son atendidas mediante dos
    decisiones de diseño: la calibración empírica del parámetro de
    contaminación a partir de evaluaciones sobre conjuntos de datos con
    tasas de anomalía conocidas, y la representación de cada instancia
    mediante un conjunto acotado de características estadísticas
    seleccionadas, que reduce la dimensionalidad del espacio de búsqueda.
    Cabe señalar que la etapa posterior de recomendaciones, basada en reglas
    de umbrales operativos, opera sobre las instancias ya identificadas
    como anómalas por el algoritmo, por lo que la decisión de detección
    recae exclusivamente en Isolation Forest. La incorporación de un
    esquema híbrido que combine el puntaje del modelo con reglas de negocio
    en la propia etapa de detección constituye una línea de trabajo futuro
    para incrementar la sensibilidad frente a degradaciones graduales.

    (Las claves Liu2008, Natterdal2024 y Zou2022 ya existen en biblio.bib,
    líneas 619, 553 y 540 respectivamente. No hace falta agregar referencias.)

3. Retention / persistencia:
   - ESTADO ACTUAL del código: NO existe base de datos (no hay PostgreSQL,
     SQLAlchemy ni psycopg en el proyecto, verificado fuera de .venv). Las
     métricas se consultan on-demand a Cloud Eye en cada análisis; los
     resultados se exportan a archivos (txt/csv/json) mediante
     src/utils/report_generator.py; el modelo se guarda con joblib.
   - PLAN PARA LA ENTREGA FINAL (informado por los autores): se incorporará
     una base de datos que almacenará, por usuario, las recomendaciones
     generadas para la infraestructura, incluyendo el código Terraform.
    - DECISIONES CONFIRMADAS POR LOS AUTORES para la entrega final:
      a) MÉTRICAS: no se persisten. En cada análisis el sistema vuelve a
         obtener las métricas desde Huawei Cloud autenticándose con las
         credenciales AK/SK del usuario. No existe retention propio de
         métricas: la disponibilidad histórica queda limitada por la política
         de retención de Cloud Eye.
      b) RECOMENDACIONES: se persisten en base de datos. Cada recomendación
         incluye el código Terraform generado y una descripción que documenta
         la anomalía detectada y la acción propuesta. La trazabilidad del
         análisis vive dentro del Terraform + descripción, no en tablas
         normalizadas de análisis/resultados.
      c) ARQUITECTURA DE BD: base de datos ÚNICA con registros asociados a
         cada usuario (no una BD separada por usuario).
